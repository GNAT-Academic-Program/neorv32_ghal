# neorv32

GHAL MCU crate for the NEORV32 RISC-V softcore: registers and driver bodies
for bare-metal Ada.

This is the software counterpart of
[neorv32_mercury2](https://github.com/GNAT-Academic-Program/neorv32_mercury2),
and the NEORV32 equivalent of
[stm32f746_ghal](https://github.com/GNAT-Academic-Program/stm32f746_ghal).

## NEORV32 version

This crate is written for **NEORV32 v1.13.6** and no other release.

- The registers in `src/svd` are generated from the SVD file of v1.13.6.
- `NEORV32_System.Expected_Version` holds the matching hardware version,
  `16#0113_0600#`.
- `NEORV32_System.Version_Matches` compares it with the version the loaded
  bitstream reports. The board calls it at startup.

NEORV32 changes its registers between releases. A driver built for one
release, running on a bitstream of another, fails in ways that are hard to
trace. The check makes that failure explicit.

## SoC requirements

The bitstream must provide:

| Requirement | Why |
|---|---|
| NEORV32 v1.13.6 | register layout |
| A extension (Zaamo) | GPIO changes one pin in a single, uninterruptible instruction |
| SYSINFO | clock frequency and the list of implemented peripherals are read from it |

The GAP SoC profile (`rv32imac`, see neorv32_mercury2) meets all three.

## What is in the crate

| Package | Role |
|---|---|
| `NEORV32.*` (`src/svd`) | registers of every NEORV32 peripheral, generated by svd2ada |
| `NEORV32_System` | what the SoC reports about itself: version, clock, memory sizes, implemented peripherals |
| `NEORV32_GPIO` | GPIO driver body, shaped to fit `gpio_generic` |
| `Gpio` | `Gpio_Interface` instantiated with `NEORV32_GPIO` |
| `NEORV32_UART` | UART driver body (UART0 or UART1), shaped to fit `usart_generic` |

Peripherals with registers but no driver yet: SPI, SDI, TWI, TWD, PWM, WDT,
TRNG, GPTMR, ONEWIRE, NEOLED, DMA, SLINK, CLINT, CFS, TRACER, SMC.

## Architecture

```
Application
    |
Board crate (instantiates everything, knows the wiring)
    |
MCU crate (neorv32)   <- this crate
    |
Generic interfaces (gpio_generic, usart_generic, ...)
```

The MCU crate supplies driver bodies. It does not decide which UART is the
console or which pin is an LED. The board crate does, in two stages.

```ada
with NEORV32_System;
with NEORV32_UART;
with Usart_Interface;

package Instances is

   --  Stage 1: driver meets silicon.
   package UART_0_HW is new NEORV32_UART (Port => NEORV32_System.UART0);

   --  Stage 2: silicon meets contract.
   package Console is new Usart_Interface
     (Driver_Init    => UART_0_HW.Init,
      Driver_Enable  => UART_0_HW.Enable,
      Driver_Disable => UART_0_HW.Disable,
      Driver_Reset   => UART_0_HW.Reset,
      Driver_Tx_Push => UART_0_HW.Tx_Push,
      Driver_Rx_Pop  => UART_0_HW.Rx_Pop);

end Instances;
```

GPIO pins are plain values:

```ada
with Gpio;
with NEORV32_GPIO;

Led : constant Gpio.Pin := NEORV32_GPIO.Make_Pin (0);
```

## Clock

NEORV32 has one clock. Its frequency is a generic of the gateware, and the
SoC reports it in SYSINFO. `NEORV32_System.Clock_Hz` reads it.

There is no clock tree to configure and no value to keep in sync between the
gateware and the software. `NEORV32_UART` uses `Clock_Hz` by default. A board
can pass another function as `Get_Clock`.

## Behavior to know

### UART

- The frame is fixed by the hardware: 8 data bits, no parity, 1 stop bit.
  Any other request raises `Usart_Types.USART_Unsupported`.
- RTS/CTS flow control is supported.
- A baud rate the clock cannot produce within 2 % raises
  `Usart_Types.USART_Unsupported`.
- Using a UART that is not in the bitstream raises `Usart_Types.USART_Error`.
- Reading the DATA register removes one byte from the RX FIFO. This is why
  `Tx_Push` writes the whole register in one store. A field assignment
  (`Periph.DATA.UART_DATA_RTX := ...`) would read the register first and
  lose a received byte.
- Reading the CTRL register clears the RX overflow flag.

Baud rates with a 50 MHz clock:

| Rate | Produced | Error |
|---|---|---|
| 1200 | 1200 | 0.0 % |
| 2400 | 2396 | 0.2 % |
| 4800 | 4793 | 0.2 % |
| 9600 | 9600 | 0.0 % |
| 19200 | 19201 | 0.0 % |
| 38400 | 38402 | 0.0 % |
| 57600 | 57604 | 0.0 % |
| 115200 | 115207 | 0.0 % |
| 230400 | 229358 | 0.5 % |
| 460800 | 462963 | 0.5 % |
| 921600 | 925926 | 0.5 % |
| 1000000 | 1000000 | 0.0 % |
| 2000000 | refused | 3.8 % |

### GPIO

- Pins are numbered 0 .. 31. How many exist and where they go is decided by
  the gateware.
- Output N and input N are two separate wires of the SoC. `Set`, `Clr` and
  `Toggle` drive output N. `Read` samples input N. They are the same
  physical pin only when the gateware joins them.
- No pull resistors, no open drain, no alternate functions. Asking for one
  raises `Gpio_Types.GPIO_Unsupported`. Pulls are set in the FPGA
  constraints.
- The port has no set/clear registers. `Set`, `Clr` and `Toggle` use the
  atomic instructions `amoor.w`, `amoand.w` and `amoxor.w`, so two tasks or
  an interrupt changing different pins never lose a change.
- `PORT_DIR` only exists when the gateware enables `IO_GPIO_DIR_EN`.
  Without it, output N is always driven.

## Integration

Add to the `alire.toml` of the board crate:

```toml
[[depends-on]]
neorv32 = "*"

[[pins]]
neorv32 = { url = "https://github.com/GNAT-Academic-Program/neorv32_ghal.git", branch = "main" }
```

## Regenerating the registers

Only when the whole stack moves to a new NEORV32 release.

1. Copy `neorv32/sw/svd/neorv32.svd` from the neorv32_mercury2 repo to
   `src/svd/neorv32.svd`.
2. Run [svd2ada](https://github.com/AdaCore/svd2ada) from the root of this
   repo:

```
svd2ada -p NEORV32 -o src/svd src/svd/neorv32.svd
```

3. Update `Expected_Version` in `src/system/neorv32_system.ads`.
4. Review every driver against the new registers.

## Adding a driver

1. Find the generic interface crate (`spi_generic`, `i2c_generic`, ...) and
   read its formals. They are the contract.
2. Write a driver package in `src/<peripheral>/` whose subprograms fit those
   formals, using the registers in `NEORV32.<peripheral>`.
3. In `Init`, check `NEORV32_System.Is_Implemented` before the first
   register access.
4. Check each register for read side effects before using field
   assignments. Fields are read-modify-write.
5. Do not instantiate the generic interface here. That is the board's job.
